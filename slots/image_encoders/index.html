    Image encoders¶

    Words such as seed, contract, preset, adapter, label set and point painting are explained in the slot index.

    Which of these options fit a method

    Every method has a page that lists the options of each of its slots with what was measured for each (the verdict, the levels composes, runs, learns and predicts, the class, the grasps, the reason of a refusal): HGGD (image encoder). In a terminal: grasppanda compose gsnet/gsnet_sunet14_g1b-realsense_10e --list image_encoder.

    Class: one run, seed 0, 20 iterations, 8 frames of one scene; a class counts verdicts, not accuracy. Where this page names a class or a measured verdict, it is one of the measured classes.

    The slot model.image_encoder: the network that turns the colour (or RGB-D) image into feature maps. Registry IMAGE_ENCODERS, base class grasppanda.models.image_encoders.ImageEncoder.

    No AP is claimed for anything on this page. Every option below was built, trained for 20 iterations on eight real frames and asked to predict (grasppanda probe). That shows it works; how good it is takes a full training run.

    1. The task of the slot¶

    An image encoder is the 2-D counterpart of a scene encoder: image in, a short list of feature maps out. It knows nothing about grasps. Two stages consume it:

    • HGGD (model.image_encoder of the detector). HGGD's image network is encoder → decoder → five map heads: the grasp-centre heat-map at full resolution, and at the proposal stride (8) the in-plane angle classes with three offsets per class. The decoder map at the proposal stride is also the feature map the region stage attaches to its points. Until now the encoder was fixed (ResNet-34 block layout at an eighth of the width, 1.6 M parameters, from scratch); it is now any registered image encoder.
    • The seed-based family (GSNet, EconomicGrasp, FineGrasp, GraspNet-baseline, Scale-Balanced-Grasp) reads points only. The adapters ImagePainted and ImagePaintedSubsampled put an image encoder next to their scene encoder: every point reads the image features at its own pixel (point painting, section 5).

    2. Input and output¶
    input image: (B, in_channels, H, W), float, upright (rows are image rows)
    input_layout what the channels are: rgb = colour in [0, 1], not normalised (the encoder normalises with the statistics its weights expect); rgbd = the same followed by one depth channel in metres; drgb = HGGD's own order [depth, R, G, B], the reference encoder only
    output a list of (B, out_channels[i], h_i, w_i) maps, finest first
    out_strides, out_channels nominal stride (H / h_i, rounded) and width of every map; the bridges measure them with one forward pass at construction

    What the neighbours require:

    • HGGD hands over its network image, (B, 4, U, V) = [depth, R, G, B] with u along the width (640 × 360 by default), depth in metres with the mean removed and clipped to ±1. For any encoder but the reference one, ImageNet turns the image upright ((B, C, 360, 640)), re-orders it to the encoder's layout (colour first; depth last for rgbd, dropped for rgb), and turns the maps back. The maps may have any strides and widths: a pyramid decoder projects every map to model.encoder.decoder_channels, merges them top-down, resamples to exactly image / proposal.stride (80 × 45) and goes to full resolution with transposed convolutions. So a four-level pyramid, a five-level pyramid and a single-stride ViT all fit; nothing is refused for its strides.
    • The reference encoder (HGGDResidualEncoder) keeps the reference decoder (transposed convolutions with additive skips, laid out for 640 × 360). With it the model is the one of the shipped config: same parameter names (converted checkpoints load), same seeded initialisation (tests/unit/test_image_encoders.py).
    • Point painting needs input_layout: rgb (the points already carry the depth), the colour image, the camera matrix and points in the camera frame.

    What the config checker does: image_encoder is a typed slot (Cfg[ImageEncoder]), so a node is checked against the constructor of its class before anything is built (unknown options, wrong value types, depth: rgbd instead of one of the three modes). Contract problems that need the built model are raised at build with the way out, for example encoder.base_width set next to a foreign encoder.

    RGB-D, honestly¶

    No library ships weights that were pretrained on RGB-D, and timm's in_chans=4 only repeats the colour filters. So depth is an explicit option of every bridge, depth:

    depth What the encoder sees Pretrained weights
    rgb_only (default of the presets) colour; in_channels 3 used exactly as released. HGGD's heat-map then has no depth cue; depth still reaches the region stage as points
    fourth_channel colour + depth; the first convolution (or patch embedding; all parallel stem convolutions of FastViT / RepViT) gets a fourth input colour filters as released; the depth filters start at zero (depth_init: zero: the network starts as the colour model) or at the mean colour filter (depth_init: mean) and are always trained, also with frozen: true
    depth_stem colour + a 3-channel residual computed from depth by a small stem of its own (two convolutions, the last starts at zero) untouched; with frozen: true only the stem and the consumer's decoder learn

    All of them fit HGGD (class 1 of 1 probed: HGGD is the one method with this slot) in the sense that matters here: the pyramid decoder takes any strides, so the only method-specific option is hggd-residual, whose decoder is laid out for HGGD's image size. None of them applies to a seed-based method directly; those use an image encoder through point painting (section 5), which takes the same nodes with depth: rgb_only.

    The three bridge classes expose far more than the presets: TimmImageEncoder(name=<any timm model with features_only>), HFImageEncoder(name=<hub id or local directory>), TorchvisionImageEncoder(name=<resnet*, regnet*, or a model with .features>).

    4. How to use an option (HGGD)¶

    grasppanda compose --list image_encoder prints every preset of this slot with its one-line summary; grasppanda compose --show image_encoder=<name> prints one in full.

    One command writes a config, a second one tries it on real frames:

    $ grasppanda compose hggd/hggd_r34w8_g1b-realsense_15e --set image_encoder=resnet34 -o hggd_resnet34.yaml
grasppanda compose hggd/hggd_r34w8_g1b-realsense_15e --set image_encoder=resnet34

what compose did
  • image_encoder: preset `resnet34` (TimmImageEncoder). ResNet-34 from timm with ImageNet-1k
    weights, colour only.

  - contracts: HGGD is not built on the seed-based skeleton, so there are no stage contracts to
    compare; the config check below is the verdict.

    The same thing as a YAML fragment, in a config that inherits the HGGD config:

    model:
  encoder:
    decoder_channels: 64            # width of the pyramid decoder and of the region features
  image_encoder:
    type: TimmImageEncoder
    name: resnet34.a1_in1k          # any timm name: python -c "import timm; print(timm.list_models('resnet*'))"
    pretrained: true                # timm downloads; or  checkpoint: /path/to/file.safetensors
    depth: rgb_only                 # rgb_only | fourth_channel | depth_stem
    frozen: false                   # true: fixed encoder, only the depth handling and the decoder learn

    Change one option of a preset on the command line:

    $ grasppanda compose hggd/hggd_r34w8_g1b-realsense_15e --set image_encoder=dinov2-small-reg \
    --opts model.image_encoder.depth=depth_stem model.image_encoder.frozen=true

    The settings that matter, and how to choose them:

    Setting Where How to choose
    depth every bridge rgb_only to use pretrained features as they are; fourth_channel for convolutional pyramids you fine-tune; depth_stem when the encoder is frozen
    frozen every bridge true for foundation ViTs (DINOv2/v3, SigLIP 2, RADIO) and small data; batch-norm statistics stay fixed too
    out_indices timm, transformers which levels come out. Pyramids: all (default). ViTs: timm returns the last three blocks, HFImageEncoder the last one; [3, 6, 9, 12] gives the decoder four depths to merge
    input_size every bridge models with one fixed size (MaxViT, Hiera, EVA-02, timm's DINOv2 and SigLIP): the image is resampled to it and the model is built for it with model_args: {img_size: [H, W]}. Choose multiples of 32 (pyramids) or of the patch size near 360 × 640
    size_multiple every bridge models that take any multiple of their patch or window (DINOv3: 16; HF DINOv2: 14; SAM 2 Hiera and HF Swin V2: 32): the image is resampled up to the next multiple
    model_args every bridge free-form arguments of the library (timm.create_model, from_pretrained, torchvision.models.get_model) as one mapping: drop_path_rate, window_size, trust_remote_code …
    model.encoder.decoder_channels HGGD 64 by default (the reference network has 32 at the proposal stride). Wider helps a wide encoder, costs memory in the region stage
    model.encoder.detach_features HGGD true (reference recipe): the region loss does not train the image network

    Pretrained weights:

    • timm: pretrained: true downloads the tag's weights from the hub (HF_HOME chooses the cache). A local file: checkpoint: /path/file.safetensors (timm's key names; tried here with a local file of vit_small_patch16_dinov3.lvd1689m). Random weights: pretrained: false.
    • transformers: name is a hub id or a local directory with config.json and weights; pretrained: false builds the architecture from its configuration alone; config: {model_type: dinov2, …} builds from a configuration you write, without any download.
    • torchvision: weights: DEFAULT (or the name of a weight enum entry), weights: null for random weights, checkpoint: for a local state dict.
    • Every probe on this page ran with the pretrained weights named in the table, downloaded in this session, except the three presets whose weights are non-commercial (convnextv2-tiny, convnextv2-atto, hf-hiera-tiny): their presets keep the weights off and were probed on random weights. Random weights were otherwise used only by the unit tests.
    • What is fetched, and when. A bridge with pretrained: true (or weights: for torchvision) lets its library download the weights on first use and prints one line to standard error with the name and the licence the library states (NON-COMMERCIAL where it says so). Nothing else in the toolbox downloads weights. A preset never switches non-commercial weights on by itself, and a model that runs code from its hub repository (model_args: {trust_remote_code: true}, here hf-radio-v3-base) is refused by the config check until the config also says accept_remote_code: true.

    5. Point painting: image features for the seed-based methods¶

    ImagePainted (wraps a dense scene encoder) and ImagePaintedSubsampled (wraps a subsampled one) encode the colour image once, project every point into it with the camera matrix, sample the feature maps there bilinearly and hand the result to the 3-D network:

    • fusion: input: as extra input channels. The wrapped encoder's in_channels is what the detector feeds plus paint_channels (GSNet: 3 constant ones + 32 = 35).
    • fusion: output: as a zero-initialised residual on the encoder's output features (sampled at the output points, so it also works after sub-sampling). in_channels stays as it was.

    What the data pipeline delivers, and what it does not (checked in grasppanda/datasets/scene.py, grasppanda/transforms/frame.py, grasppanda/structures/observation.py):

    • images: [rgb] on a scene dataset puts the colour image into observation.rgb ((B, 3, H, W) in [0, 1]); observation.intrinsics is always there; points are in the camera frame. The pixel of a point is therefore its projection, and sub-sampling does not matter. This is all the adapter uses, and it needed one additive change of the skeleton: a scene encoder that declares uses_observation = True is called as backbone(points, feats, observation).
    • Missing: painting under point-space augmentation. A dataset that serves images refuses RandomFlip and RandomRotation (a moved cloud no longer projects onto its image). The per-point pixel index exists inside the pipeline (PointSample.pixels, it survives sampling) but is not part of Observation. Carrying it into the batch (one field, one line in to_batch and in collate) and letting the rigid transforms pass when only pixel-indexed image data is present would lift the restriction. Not done here: it changes the data contract of every method.
    • Not built: compose support. --set backbone= takes encoders, not wrappers, and a painted config also has to change the dataset node of every split. So painting is a YAML fragment you write, not a compose choice; the presets image-painted and image-painted-subsampled under grasppanda/presets/backbone/ hold the nodes.

    The complete fragment for GSNet (a file next to the shipped configs, here configs/experimental/my_gsnet_painted.yaml):

    _base_:
  - ../gsnet/gsnet_sunet14_g1b-realsense_10e.yaml

model:
  backbone:
    _delete_: true                  # replace the base config's encoder node
    type: ImagePainted              # ImagePaintedSubsampled around PointNet2 / PointNet2Transformer
    fusion: input                   # input | output
    paint_channels: 32
    image_scale: 0.5                # encode 640 x 360 instead of the 1280 x 720 sensor image
    image_encoder:                  # any image-encoder node with depth: rgb_only
      type: TimmImageEncoder
      name: resnet18.a1_in1k
      pretrained: true
      out_indices: [1, 2]           # strides 4 and 8
      depth: rgb_only
    backbone:
      type: SparseUNet14
      in_channels: 35               # 3 constant ones + 32 painted channels
      out_channels: 512
      voxel_size: 0.005

data:
  train:
    dataset:
      images: [rgb]
      transforms:                   # the base list without RandomFlip and RandomRotation
        - {type: RandomSample, num_points: 15000}
        - {type: FilterObjects, min_visible_points: 50}
        - {type: SampleGraspLabels, point_fraction: 0.25, min_points: 300, collision: zero_scores, grids: deferred}
        - {type: ConstantFeatures, channels: 3}
  val: {dataset: {images: [rgb]}}
  test: {dataset: {images: [rgb]}}

    6. Pitfalls actually met¶

    • HGGD's image is transposed. Its tensors are (B, C, U, V) with u along the width. A pretrained network fed that tensor sees a mirrored, rotated picture. ImageNet therefore turns the image upright for every encoder but its own; an encoder written for this slot always gets (B, C, H, W).
    • in_chans=4 of timm is not RGB-D pretraining; it repeats the colour filters. The bridges do not use it (section 2).
    • Fixed-size transformers. timm's DINOv2, EVA-02, SigLIP, MaxViT and Hiera assert the image size they were built for; 360 is not a multiple of 14, 16 or 32. input_size / size_multiple resample the image; the presets carry values that ran.
    • Swin V2 in timm needs every stage to be a multiple of its window: 384 × 640 with windows of 6 × 10 cells ran (swinv2-tiny); the transformers implementation pads by itself (hf-swinv2-tiny).
    • Hiera: the MAE checkpoints (hiera_*_224.mae* in timm, facebook/hiera-*-224-hf) have position embeddings for 224 × 224 only. hf-hiera-tiny runs by squeezing the image to that square; hiera-small-abswin and sam2-hiera-tiny take the image at its size.
    • Channels-last maps: timm's Swin returns (B, h, w, C); with 96 channels and a 96-row map the two cannot be told apart by shape. The bridge reads timm's declared output format.
    • Re-parameterisable stems (FastViT, RepViT) read the image with several parallel convolutions; fourth_channel widens all of them. Convolutions are widened in place, so TensorFlow-style "same" padding (MaxViT, EfficientNetV2) keeps working.
    • Depth Anything V2 is a depth-estimation model on the hub, not a backbone: api: depth_backbone takes the DINOv2 encoder out of it; its backbone returns tokens, which the bridge reshapes.
    • Gated repositories: Meta's own DINOv3 repositories on the hub answer 401 without an accepted licence and a token. timm's mirrors of the same weights are not gated and are what the presets use.
    • The config hash of the HGGD configs changed although the model did not: the hash covers the resolved config including defaults, and the detector has one more option.
    • Shared GPU: several probes first failed with CUDA out-of-memory errors while other jobs filled the card; they were probed again one at a time. The peak memory in the table is this process only.
    • images is a list that a child config replaces. FineGrasp's dataset already serves images: [depth] for its normals; a painted FineGrasp config needs images: [depth, rgb]. With [rgb] alone the first batch stops with "DepthNormals needs the depth image of …; configure the dataset with images: [depth]".
    • A nested encoder node gets its defaults filled in by the config loader, so a wrapper cannot inject in_channels into the encoder it wraps; the painted adapters read it from the wrapped node instead (section 5).

    7. Not wrapped¶

    • MambaVision (nvidia/MambaVision-T-1K, weights also on this machine). Its hub code stops with "requires the following packages that were not found in your environment: mamba_ssm", a compiled CUDA extension; the card's licence is nvclv1 (non-commercial). Tried through HFImageEncoder(api: model, trust_remote_code); not built here.
    • Meta's gated DINOv3 repositories (facebook/dinov3-vits16-pretrain-lvd1689m): 401 without a token. HFImageEncoder loads them once you have access; the presets use timm's mirrors instead.
    • timm's MAE Hiera (hiera_tiny_224.mae_in1k_ft_in1k): cannot be built for another image size (position-embedding size mismatch on load). Use hiera-small-abswin.
    • RGB-D fusion encoders (two streams with fusion at every stage: CMX, CMNeXt, TokenFusion, GeminiFusion, DFormer and others; none was opened in this session): they are not a library model behind one forward(image), and each needs its own adapted source and licence check. The slot contract (input_layout: rgbd) is ready for one.
    • torchvision's transformers (Swin, ViT, MaxViT): TorchvisionImageEncoder cuts chains of stages only and says so; timm has the same architectures.
    • Decoder injection for point painting (image features added at every level of the 3-D decoder, as DITR does; its code was not opened in this session): it needs the wrapped encoder to expose its levels. Input and output fusion are what is offered.
