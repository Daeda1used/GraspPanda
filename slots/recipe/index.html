    The training recipe: optimizer, schedule, hooks, augmentation¶

    Words such as seed, contract, preset, adapter, label set and point painting are explained in the slot index.

    Which of these options fit a method

    Every method has a page that lists the options of each of its slots with what was measured for each (the verdict, the levels composes, runs, learns and predicts, the class, the grasps, the reason of a refusal): GSNet (optimizer, schedule, hooks, augmentation, whole recipe); EconomicGrasp (optimizer, schedule, hooks, augmentation, whole recipe); FineGrasp (optimizer, schedule, hooks, augmentation, whole recipe); GraspNet-baseline (optimizer, schedule, hooks, augmentation, whole recipe); Scale-Balanced-Grasp (optimizer, schedule, hooks, augmentation, whole recipe); HGGD (optimizer, schedule, hooks, augmentation, whole recipe). In a terminal: grasppanda compose gsnet/gsnet_sunet14_g1b-realsense_10e --list optimizer.

    Class: one run, seed 0, 20 iterations, 8 frames of one scene; a class counts verdicts, not accuracy. Where this page names a class or a measured verdict, it is one of the measured classes.

    Everything on this page is around the model: how its weights are updated, how the learning rate moves, what runs before and after an epoch, and how a training sample is perturbed. None of it changes what the detector computes, so none of it is bound to one method: the same line works under GSNet and under HGGD unless the page says otherwise.

    No AP is claimed for anything here. "Runs" means: grasppanda probe trained 20 iterations on 8 real frames of GraspNet-1Billion with finite losses and predicted grasps. Whether a recipe is better takes a training run and an evaluation.

    1. The task of the slot¶

    A config has four places that make up the recipe, and each is a slot you fill by name:

    Config key Registry What it decides When it runs
    optimizer OPTIMIZERS how gradients become weight updates once per train.accumulate batches
    scheduler SCHEDULERS the learning rate over the run after every optimizer step or every epoch (train.scheduler_unit)
    hooks HOOKS anything else around the loop: weight averages, freezing, clipping variants at before_run, before_epoch, before_step, after_iter, after_epoch, after_run
    data.train.dataset.transforms TRANSFORMS augmentation of one training sample in the data-loader workers, per sample

    Plain options of the loop need no component: train.amp (mixed precision), train.accumulate (gradient accumulation), train.grad_clip with train.grad_clip_mode (clipping), train.ema (a fixed-decay weight average), train.sync_bn.

    The loop itself (grasppanda/engine/trainer.py) is short: forward and backward per batch; every train.accumulate batches before_step hooks, clipping, optimizer.step(), the weight average, the scheduler. Everything on this page plugs into those points.

    2. Input and output¶

    Optimizer. Built by build_optimizers(model, config["optimizer"]). The engine supplies two arguments a config never writes: params (every parameter with requires_grad, or what the detector's configure_optimizers returns) and, for components that ask for it, model (to name parameters). The result must be a torch.optim.Optimizer; the bridges on this page return the library's own optimizer object, so checkpoints hold its state dict unchanged. A detector may return several optimizers; each gets a scheduler of its own.

    Scheduler. Built per optimizer from the scheduler node; it must be a torch.optim.lr_scheduler.LRScheduler. The trainer calls step() once per optimizer step (train.scheduler_unit: iteration) or once per epoch (epoch, the default). The engine fills in the length of the run where the schedule needs it: total_steps of OneCycleLR and TimmSchedule, T_max of CosineAnnealingLR, total_iters of PolynomialLR. scheduler: null is a constant rate.

    Hook. A subclass of grasppanda.engine.hooks.Hook; every callback receives the TrainState (model, optimizers, schedulers, gradient scaler, ema, epoch and iteration counters, the resolved config). Hooks run in ascending priority; evaluation is 70, checkpointing 80, so a hook that changes the weights used for evaluation has a lower one. A weight average installs itself as state.ema, which is what evaluation.weights: ema scores and what a checkpoint stores under ema.

    Transform. A PointTransform maps one PointSample to one PointSample after the label-alignment boundary. A sample holds points (N, 3) float64 in metres in the camera frame (z along the view), full_points (the cloud before sampling), per-point labels aligned with points, and objects: one 4 × 4 object-to-camera pose per instance, to which the grasp labels are attached. So an augmentation may

    • remove or reorder points only through sample.gather(index), which carries the labels;
    • move the scene only together with the object poses;
    • not move points at all when the sample carries images (rgb, depth) or camera-bound extras, as HGGD's does: the config check refuses such a transform list (a transform that moves points declares moves_points = True), and the sample refuses it again.

    Scaling the scene is therefore not an allowed augmentation: grasp widths, depths and the gripper are in metres and would not follow.

    What the config checker does. grasppanda print-config --check (and compose) checks every key of these nodes against the constructor signature of the named class, without importing the optional libraries. Free-form arguments of a library go into one explicit mapping, options. Whether an optimizer name exists in the installed library is known only when the optimizer is built: probe or train then names the valid ones.

    3. Options at a glance¶

    Install the optional libraries once: pip install -e ".[optim]" (timm, pytorch_optimizer, schedulefree; all Apache-2.0). Options marked "core" need nothing.

    Everything is random-init: a recipe has no weights. "Measured" is the verdict of grasppanda probe per method, from the records of Measured combinations; G = GSNet, E = EconomicGrasp, H = HGGD. The records below are of two methods, not five: the last column is the class of the measured page at the level runs, counted over the methods probed (2 of 2 probed: it ran under a seed-based method and under HGGD, a detector family with its own data path, hooks and clipping), followed by the methods not probed yet. The grid now has a cell for every preset under every method it applies to (all six; the five seed-based ones for a preset that names backbone). That column is written by tools/make_method_pages.py from the records; the other levels are on the method pages.

    Under HGGD the three encoder-specific optimizer and hook presets and the two encoder recipes have no cell: they name backbone, a module only the seed-based skeleton has. They have cells under the five seed-based methods; the records above are of GSNet and EconomicGrasp.

    4. How to use each option¶

    One line with compose¶

    grasppanda compose gsnet/gsnet_sunet14_g1b-realsense_10e \
    --set optimizer=timm-lamb --set schedule=warmup-cosine --set hooks=ema+grad-clip \
    --set augment=jitter -o my_recipe.yaml
grasppanda probe my_recipe.yaml          # about a minute: does it train and predict?
grasppanda train my_recipe.yaml
    • optimizer, schedule and recipe take one preset; hooks and augment take several joined by +.
    • Recipe slots combine with stage slots (--set backbone=ptv3 --set recipe=ptv3-adamw-onecycle) and work for HGGD, which has no stage slots.
    • --opts changes single values and wins over a preset: --opts optimizer.lr=3e-3 scheduler.warmup_steps=0.1 train.epochs=20.
    • The composed file lists what each preset says must be re-tuned.

    Optimizers¶

    optimizer: {type: AdamW, lr: 1.0e-3, weight_decay: 0.05}                    # torch.optim, by class
optimizer: {type: TimmOptimizer, name: lamb, lr: 2.0e-3, weight_decay: 0.02}
optimizer: {type: TimmOptimizer, name: lookahead_adan, lr: 1.0e-3, options: {betas: [0.98, 0.92, 0.99]}}
optimizer: {type: PytorchOptimizer, name: prodigy, lr: 1.0}
optimizer: {type: ScheduleFree, name: adamw, lr: 2.5e-3, warmup_steps: 200}
    • lr and weight_decay are arguments of the bridge; everything else the optimizer takes (betas, eps, momentum, …) goes into options.
    • Names: python -c "import timm.optim as o; print(o.list_optimizers())" and python -c "import pytorch_optimizer as o; print(o.get_supported_optimizers())". A wrong name is reported with the list of valid ones when the optimizer is built.
    • A lookahead_ prefix wraps any timm optimizer in Lookahead.
    • Learning-rate-free optimizers (prodigy, dadaptadam, …) want lr: 1.0 and usually --set schedule=constant or a cosine.
    • A schedule-free optimizer needs scheduler: null and ScheduleFreeHook; the presets schedulefree-adamw, -radam, -sgd set all three.

    Parameter groups: a pretrained encoder, layer-wise decay¶

    optimizer:
  type: ParamGroups
  optimizer: {type: AdamW, lr: 1.0e-3, weight_decay: 0.05}   # any optimizer node; must set lr
  lr_multipliers: {backbone: 0.1}      # dotted prefix of the parameter name, or "re:<regex>"
  layer_decay: 0.75                    # null: off
  layer_decay_module: backbone
  layer_decay_depth: 2
  no_decay_1d: true                    # no weight decay on biases and normalisation weights

    The rate of a parameter is lr × the first matching multiplier × layer_decay ** (L - i) for layer i of the L layers of layer_decay_module. A layer is a sub-module layer_decay_depth levels below that module, in registration order:

    sparse-unet14 depth 1: stem, down, encoder, up, decoder, project            (6 layers)
sparse-unet14 depth 2: stem.conv, stem.norm, down.0, … decoder.3, project   (19 layers)
ptv3 depth 2: embedding.stem, enc.enc0 … enc.enc4, dec.dec3 … dec.dec0      (10 layers)
ptv3 depth 3: … enc.enc0.block0, enc.enc0.block1, enc.enc1.down, …          (32 layers)

    (python -c "from grasppanda.engine.optimizers import layer_names; ..." on your own encoder.) In a U-Net the decoder is registered after the encoder and therefore counts as later layers with a higher rate. A pattern that matches nothing is an error that lists the top-level modules. OneCycleLR would overwrite all group rates with one max_lr; the engine scales a scalar max_lr per group.

    To train a pretrained encoder: load the weights (runtime.load_from=<checkpoint>, with runtime.allow_weight_mismatch=true when the checkpoint does not cover the whole detector; the page of the encoder slot says which released weights fit), then --set recipe=finetune-encoder or the single parts optimizer=encoder-lr-0.1, optimizer=layer-decay, hooks=freeze-encoder.

    Schedules¶

    scheduler: {type: OneCycleLR, max_lr: 1.0e-3, pct_start: 0.05, div_factor: 10.0, final_div_factor: 1000.0, cycle_momentum: false}
scheduler: {type: TimmSchedule, name: cosine, warmup_steps: 0.05, warmup_lr_init: 1.0e-6, lr_min: 1.0e-6}
scheduler: {type: TimmSchedule, name: multistep, warmup_steps: 1, warmup_lr_init: 1.0e-4, options: {decay_t: [6, 9], decay_rate: 0.1}}
scheduler: {type: TimmSchedule, name: cosine, options: {t_initial: 4, cycle_limit: 3, cycle_decay: 0.5}}   # restarts
train: {scheduler_unit: iteration}     # or epoch: the unit of every step count above
    • TimmSchedule.warmup_steps below 1 is a fraction of the run, from 1 on a step count.
    • warmup_lr_init and lr_min are absolute rates, not factors.
    • OneCycleLR.max_lr replaces optimizer.lr; keep cycle_momentum: false unless the optimizer has betas or momentum you want cycled.

    Hooks and train options¶

    hooks:
  - {type: EMAHook, decay: 0.999, warmup: true, interval: 1, buffers: copy}
  - {type: SWAHook, start_epoch: 7}
  - {type: FreezeHook, modules: [backbone], epochs: 2, eval_mode: true}
  - {type: AdaptiveGradClipHook, clip_factor: 0.01, exclude: [head]}
evaluation: {weights: ema}             # score the average (EMAHook, SWAHook or train.ema)
train: {amp: true, accumulate: 2, grad_clip: 1.0, grad_clip_mode: norm}
    • One weight average per run: EMAHook, SWAHook and train.ema exclude each other. EMAHook differs from train.ema in three ways: the decay warms up (min(decay, (1 + n) / (10 + n))), buffers are copied rather than averaged by default (batch-norm statistics and HGGD's learned anchors stay those of the trained model), and interval can skip steps. A resumed run continues either average exactly.
    • evaluation.weights: ema selects the average of a checkpoint in grasppanda test as well; model selects the trained weights of the same checkpoint.
    • FreezeHook sets requires_grad per epoch; an optimizer skips a parameter without a gradient, weight decay included, so nothing has to be rebuilt when the modules are released. With eval_mode the frozen modules keep their batch-norm statistics.
    • AdaptiveGradClipHook and train.grad_clip exclude each other (the preset agc switches train.grad_clip off, which matters under HGGD, whose recipe clips by value).

    Augmentation¶

    data:
  train:
    dataset:
      transforms:
        - {type: RandomDropout, ratio: 0.2, prob: 0.5}     # before the sampling step
        - {type: RandomSample, num_points: 15000}
        # ... the label steps, flip and rotation of the base config ...
        - {type: RandomShift, shift: [[-0.1, 0.1], [-0.1, 0.1], [-0.05, 0.1]]}
        - {type: RandomJitter, sigma: 0.001, clip: 0.005}

    --set augment=dropout+shift+jitter writes exactly this around the list of the base config. Units are metres in the camera frame. RandomJitter perturbs only the network input: full_points, poses and labels describe the clean scene.

    Without compose: schedule bases¶

    Three method-neutral files under configs/_base_/schedules/ can be inherited like the methods' own: adamw_onecycle_10e.yaml, adamw_warmup-cosine_10e.yaml, schedulefree-adamw_10e.yaml. They set optimizer, scheduler and train.epochs.

    5. Pitfalls¶

    • OneCycleLR and momentum. Its default cycle_momentum: true rewrites betas or momentum every step and raises for optimizers that have neither. The presets set false.
    • OneCycleLR ignores optimizer.lr. The peak is max_lr. Changing only optimizer.lr with --opts changes nothing.
    • Schedule-free and batch norm. The weights that are evaluated are an average; the batch-norm statistics were collected at the training point. The authors re-estimate them; this toolbox does not.
    • Schedule-free in a short probe. With warmup_steps: 200 a 20-iteration probe runs entirely inside the warm-up, so its losses fall more slowly than with Adam. That says nothing about a full run.
    • Per-epoch units and warm-up. With train.scheduler_unit: epoch a warm-up that starts at 0 spends the whole first epoch at rate 0; the preset multistep-warmup starts at 1e-4.
    • Lists replace. hooks and transforms of a child config replace the inherited list. compose writes the base's entries out again; a hand-written child must repeat them (HGGD needs its EpochSignalHook).
    • SWAHook.start_epoch must be below train.epochs; the run refuses to start otherwise ("nothing would be averaged").
    • Point augmentation next to images is refused by the config check. augment=jitter, augment=shift and the flip and rotation of the GraspNet recipes move the points; a dataset section that serves images or view_grasps (HGGD's) would keep them where they were. The message names the transform and the image-space data. augment=dropout removes points and moves none, so it runs under HGGD.
    • A wrong optimizer name passes the config check and fails when the optimizer is built, with the list of valid names: the check does not import the libraries.
    • Mixed precision is not ready for the ported methods, and is refused. hooks=amp (train.amp: true) failed under GSNet in the first iteration: the label assigner writes half-precision values into a single-precision tensor ("Index put requires the source and destination dtypes match"). Under HGGD the loss of the first iteration was not finite (loss/heatmap = nan, loss/angle = inf). The config check now refuses train.amp: true unless the detector class declares amp_ready = True, and none of the shipped ones does. The preset stays as the switch for a detector of your own; it is one of the 37 names on this page and not a usable option today.
    • SOAP fails under HGGD. optimizer=soap runs under GSNet; under HGGD the second optimizer step ends in "CUDA error: an illegal memory access was encountered", three times out of three. The cause was not investigated.
    • Schedule-free SGD in a short probe. Under GSNet one of the 20 iterations of the probe had no real seed (runs-unstable); the AdamW and RAdam variants did not show it.

    6. Not wrapped¶

    Candidate Link Why not
    Normalisation and activation as config keys (GroupNorm, LayerNorm, GELU, SiLU, …) torch.nn; timm create_act.py No shared layer builder exists in the stages: norms and activations are literals at dozens of sites in grasppanda/models/, outside this package's lane. A hook that swapped modules after construction would not run at grasppanda test, so trained and tested models would differ. Needs one builder used by every stage first.
    RandomScale Pointcept transform.py Grasp widths, depths and the gripper are in metres; PointSample has no way to scale the label grids with the scene.
    ElasticDistortion same file Not a rigid map: object poses, and the grasp labels attached to them, cannot follow.
    Chromatic transforms (auto-contrast, colour jitter) same file The ported methods feed no colour to the scene encoder; HGGD's image pipeline is not a point transform.
    Mix3D scene mixing Pointcept pointcept/datasets/utils.py, point_collate_fn(mix_prob) Works in the collate function, which is fixed in the engine; two scenes' object poses and label sets would have to be merged.
    Sharpness-aware minimisation (SAM) pytorch_optimizer/optimizer/sam.py (class SAM) Its step() needs a closure that runs a second forward and backward pass; the loop makes one pass per batch and calls step() without a closure.
    ReduceLROnPlateau, timm PlateauLRScheduler PyTorch, timm Step on a monitored metric, which the trainer does not hand to schedulers. Refused by name.
    timm's learning-rate noise timm.scheduler TimmSchedule evaluates the closed form so that a resumed run needs no state of timm's; the noise is applied in timm's own step().
    Batch-norm re-estimation after SWA (torch.optim.swa_utils.update_bn) PyTorch It iterates a loader of tensors; batches here are Batch objects and the detectors compute losses, not plain forwards.
