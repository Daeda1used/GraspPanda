    HGGD¶

    Own family RA-L 2023 RGB-D input equal to the reference ✓ authors' weights scored here

    From an RGB-D image, it predicts a heat-map of grasp centres in 2-D, lifts each peak to 3-D and completes the grasp with a PointNet over a ball of scene points.

    Paper · Reference code · Configs, results and notes

    Run HGGD in five minutes¶

    Four steps from the authors' checkpoint to grasps. A test parses each command and runs the demo and the Python code on a toy detector of the method's family.

    1. Get the weights¶

    GraspPanda publishes no weights for HGGD: the file to download is the authors' checkpoint, under its licence. Download HGGD_realsense_checkpoint (Tsinghua Cloud) and convert it once, from the root of a GraspPanda checkout:

    python -m tools.convert_checkpoint HGGD_realsense_checkpoint hggd_realsense.pth \
    --source-format hggd --camera realsense
    Licence, checksum and what the converter writes
    • Licence: MIT (the upstream repository); trained on GraspNet-1Billion (CC BY-NC-SA 4.0)
    • SHA-256 of the download: b95da06d8723298ad28e4c720c3a6a8af73dfe6f2e8126f43de8845bf62ad6df
    • What the converter writes: hggd_realsense.pth, every tensor of the downloaded file under the name of the module that plays its role here, no value changed, with a note of the file it came from. A tensor left over or missing stops the conversion with a report; nothing is ever loaded partially. The converter is a tool of the repository; it is not installed with the package.

    2. Grasps on the example scene¶

    grasppanda demo hggd/hggd_r34w8_g1b-realsense_15e \
    --weights hggd_realsense.pth --example --collision-filter

    --example is a synthetic table-top scene shipped with GraspPanda: no dataset, no download. 14.5 s for the whole command, 72 grasps kept (one NVIDIA RTX A6000 shared with other jobs).

    What it prints and writes, and every measured run

    The command prints the config and its hash, how the weights loaded (every tensor matched, none missing), the test pipeline, the cloud, how many grasps the model predicted and how many the collision filter left (the config's variant cd: ModelFreeCollisionFilter then GraspNMS), and the ten best grasps. It writes into work_dirs/hggd_r34w8_g1b-realsense_15e/demo/:

    • grasps.npy: the grasps that are left, (G, 17) float32 in the GraspNet layout, best first, camera frame, metres;
    • grasps.png and grasps.gif: the cloud with the 30 best grasps, still and swinging around the scene;
    • example/: the scene as files (depth.png, rgb.png, mask.png, intrinsics.txt).

    Measured with the authors' checkpoint, converted: 14.5 s for the whole command; 25,600 points to the model; 470 grasps predicted, then 287 after ModelFreeCollisionFilter → 72 after GraspNMS (2026-10-15, commit ea6268b, one NVIDIA RTX A6000 shared with other jobs). Run again at commit 0ddca31 (2026-10-15): the same counts, 16.9 s.

    From Python (step 3): 72 grasps, 8.2 s for the script (2026-10-15, commit 0ddca31, one NVIDIA RTX A6000 shared with other jobs).

    3. From Python, a browser or your camera¶

    from grasppanda import GraspInferencer
from grasppanda.apis import example_scene
scene = example_scene()  # the scene of --example
inferencer = GraspInferencer(
    "hggd/hggd_r34w8_g1b-realsense_15e", "hggd_realsense.pth"
)
grasps = inferencer(
    depth=scene.depth, intrinsics=scene.intrinsics,
    depth_scale=scene.depth_scale, rgb=scene.rgb, collision_filter=True,
)
print(len(grasps), grasps.sort_by_score().to_graspnet_array()[:3])

    It runs the demo's pipeline on the demo's scene and returns its 72 grasps. HGGD reads the colour image (rgb=) and takes no mask. More: From Python.

    # ~/grasppanda_weights: the folder that holds hggd_realsense.pth
grasppanda explore --weights-dir ~/grasppanda_weights

    Open http://127.0.0.1:8765/ and choose HGGD in the Run tab: hggd_realsense.pth is chosen for you by its name. Keep the example scene or upload a depth image with its intrinsics, and press Run: the page shows the picture, the best ten grasps, the counts through the post-processing and the command that does the same in a terminal. The server listens on your machine only and downloads nothing: Run in the browser.

    grasppanda demo hggd/hggd_r34w8_g1b-realsense_15e \
    --weights hggd_realsense.pth \
    --depth work_dirs/hggd_r34w8_g1b-realsense_15e/demo/example/depth.png \
    --intrinsics work_dirs/hggd_r34w8_g1b-realsense_15e/demo/example/intrinsics.txt \
    --rgb work_dirs/hggd_r34w8_g1b-realsense_15e/demo/example/rgb.png \
    --collision-filter --out work_dirs/camera

    The scene files of step 2 stand in for a camera. HGGD reads the colour image registered to the depth image (--rgb) and crops no workspace. Units, frames, the depth scale and the intrinsics: Your own camera.

    4. A first number on the benchmark¶

    With GraspNet-1Billion on disk (Datasets), score every 64th frame of the seen test scenes, 120 frames:

    grasppanda test hggd/hggd_r34w8_g1b-realsense_15e \
    --weights hggd_realsense.pth \
    --opts data.test.dataset.split=test_seen data.test.dataset.frame_step=64 \
    evaluation.num_workers=4

    Measured with the authors' checkpoint, converted: AP 58.16 without the collision filter and 64.14 with it, within 0.44 AP of the whole split.

    What it prints, and every measured run against the whole split

    It prints AP, AP0.8 and AP0.4 for every variant of the config, raw (the predictions as they are) and cd (with the collision filter), and writes a result record per variant into the run directory under work_dirs/. Testing needs no derived asset; the evaluator extracts a cache from the dataset's object models the first time it runs, which the times below do not include.

    How to swap, and how to read these lists

    Swap one option in with a single line, or list the options of a slot:

    grasppanda compose hggd/hggd_r34w8_g1b-realsense_15e \
    --set <slot>=<option> -o swap.yaml
grasppanda compose hggd/hggd_r34w8_g1b-realsense_15e --list <slot>

    The summary table:

    • Composes: the options the config check accepts under HGGD, the one it ships included. needs consent: an option it holds back until you accept the code it downloads (the row says how), neither accepted nor refused. no record: never composed; the row says why.
    • Refused: the options the config check refuses under HGGD; each row gives the first sentence of the reason.
    • Runs here: the swaps whose probe trained on real frames under HGGD without an error, out of every option tried there as a swap: a refusal counts, the option the method ships does not. Not counted either: encoder-lr-0.1, layer-decay, freeze-encoder, finetune-encoder and ptv3-adamw-onecycle, refused under HGGD with no probe record. Does it run? counts the same way.

    The lists of each slot:

    • Runs: the methods under which the swap trained on real frames without an error, out of every method it is a swap under; the methods that ship the option are own and not counted. Who is left out, and why, stands under the chip, or below the table when it is long. Measured: 20 training iterations on 8 RealSense frames of GraspNet-1Billion (one scene), seed 0, one run per cell; nothing was measured on GraspClutter6D or on Kinect frames.
    • Trains like shipped: trained 250 iterations beside the component the method ships, its losses fall as theirs do, out of the methods it was compared under; a method under which the swap did not run, or where it trained on a schedule of its own, is named and not counted. Level 2 needs runs, not learns: a term flat after 20 iterations can fall by 250. Measured: 250 iterations on 8 RealSense frames of GraspNet-1Billion (one scene), seed 0, at a constant learning rate (FineGrasp: its own warm-up), beside the method as shipped trained the same way twice.
    • Under HGGD: ✓ when it reached every level here; level ? (as shipped) when HGGD as shipped does not reach that level either (a note below the table says why), so the level says nothing about the option; else the level it missed and why (composes, runs, learns, predicts), or why it was refused.

    The levels, the refusal kinds and the thresholds: How we measure; every record: Does it run?; every comparison at level 2: Does it train like the shipped component?.

    How this port differs from the reference
    • One model instance trains and predicts; the mode selects the proposal budget.
    • Camera intrinsics come from the frame, not from per-camera constants rounded to two decimals.
    • A frame without proposals, or whose regions all lack support, yields an explicit empty group (the reference writes no file, or fails). A training batch without regions still trains the image network (the reference skips the step).
    • Gradient accumulation averages the two batches where the reference sums them, so the value clip is 0.5 instead of 1 (AdamW is invariant to the scale). The reference's first step of an epoch spans three batches and it drops the gradient of the last batch; neither is reproduced.
    • In-training evaluation uses the val_dev scenes, not test scene 100.
    • The anchor label pool is per process: under torchrun each process moves its own copy of the anchors. Train the reference recipe on one GPU.

    How it was checked, stage by stage: tests/integration/test_hggd_parity.py and the README.
