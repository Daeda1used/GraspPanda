    Operators and their backends¶

    grasppanda.ops holds the geometric operators the models are built from. Each has a pure-PyTorch reference implementation that runs on any device and defines the result. Four of them can also run on optional compiled kernels (C++/OpenMP and CUDA), which are used only where they return exactly what the reference returns.

    Nothing on this page is needed to use GraspPanda: after a plain pip install without a compiler every operator runs on the reference. The kernels make inference and training faster; they never change a result.

    Conventions¶

    The conventions are part of the contract: which point wins a tie decides which seeds a checkpoint sees, so a ported checkpoint only reproduces if they are kept.

    Operator Result Rules a backend must reproduce
    furthest_point_sample(points, num_samples, skip_near_origin, tie_break) (B, num_samples) indices The first sample is index 0. The squared distance is x² + y² + z² added left to right. tie_break="lowest_index" takes the first of several equally far points; "pointnet2_cuda" takes the one the PointNet++ CUDA kernel takes (bit-reversed thread id, then index, with min(512, 2^⌊log₂N⌋) threads). skip_near_origin never picks a point with squared norm ≤ 1e-3 after the first.
    ball_query(query, support, radius, nsample) (B, M, nsample) indices, (B, M) hit counts Strictly inside: d² < radius². The first nsample hits in index order; missing slots repeat the first hit; a query without hits returns index 0 in every slot and a count of 0.
    cylinder_query(query, support, rotation, radius, hmin, hmax, nsample) as ball_query With d = Rᵀ(p − q): hmin < d.x < hmax and d.y² + d.z² < radius², all strict; the axis is column 0 of rotation. Same ordering and padding.
    knn(query, support, k) (B, M, k) distances and indices Ascending Euclidean distance; equidistant neighbours in index order (a stable sort); indices start at 0.

    three_interpolate, inverse_distance_weights, voxelize, grasp_nms, the view templates and the serialisation codes have a single implementation.

    Backends¶

    Backend What runs When
    reference The pure-PyTorch operator. Always available.
    compiled The kernels of grasppanda._ops. A library has been built and its self-check passed on the device. Selecting it explicitly is an error otherwise.
    auto (default) compiled where it is available and passed its self-check, else reference.

    The kernels take float32 tensors on a CPU or a CUDA device. Other floating types always run the reference, as does knn when gradients are requested or k > 64, and cylinder_query under autocast or with TF32 matrix products (see below).

    What "identical" means, and how it is ensured¶

    A kernel has to return the same integers as the reference for every input, and the same distances bit for bit. That is checked three times:

    1. By construction. Every kernel expression mirrors one expression of the reference (grasppanda/_ops/src/common.h):
    2. no fused multiply-add: a fused a·b + c rounds once where PyTorch rounds twice (-ffp-contract=off on the host, __fmul_rn / __fadd_rn on CUDA);
    3. three-term sums in PyTorch's order. Where the reference spells the order out (furthest point sampling) so do the kernels. Where it calls sum(-1) (ball query, kNN) PyTorch adds left to right on the CPU but (x + z) + y on CUDA, and the kernels follow the device;
    4. thresholds are rounded to float32 the way PyTorch rounds a Python number that is compared with a float32 tensor;
    5. the root of a kNN distance is taken by PyTorch, not by the kernel: PyTorch's float32 square root on the CPU is accurate to one unit in the last place but is not the correctly rounded one (it differed in 18 % of a million random values);
    6. NaN and infinite coordinates behave as in torch.minimum, argmax and sort.
    7. At run time. The first time an operator runs on a device, its kernel is compared with the reference on small random and lattice clouds (ties, repeated points, empty and oversized neighbourhoods, points exactly on a surface), and the kernels' squared distances are compared with PyTorch's bit for bit. A kernel that differs is not used; one log line says so.
    8. In the test-suite. tests/unit/test_ops.py runs every oracle test on both backends; tests/unit/test_ops_equivalence.py and tests/integration/test_ops_cuda.py compare the backends on some 2 700 (CPU) and 4 700 (CUDA) randomized calls; the GSNet stage-parity and backbone-oracle tests run with the kernels as default.

    The cylinder query¶

    The reference rotates the offsets with a batched matrix product, that is through a BLAS whose rounding is not specified: MKL and cuBLAS return different last bits for the same input. No kernel can reproduce that. The cylinder kernel therefore computes its own rotated offset together with a bound on how far any correct float32 evaluation can be from it, and gives a verdict only for support points that are further from the cylinder surface than that bound. A query that meets a point inside the band before it is complete is handed back and answered by the reference itself. On recorded GraspNet-1Billion frames that happens to 2 of 4096 queries, on synthetic table tops to 13 of 65 536; the result is the reference's in every case.

    Under autocast, or with torch.backends.cuda.matmul.allow_tf32, the reference's matrix product runs in half precision or TF32. The kernel is then not used, because a float32 kernel would be more accurate than the reference and so disagree with it.

    Selecting a backend¶

    In a config, per operator (fps, ball_query, cylinder_query, knn); operators that are not mentioned use auto:

    runtime:
  ops: {fps: reference, knn: compiled}

    The values are validated when the config is loaded. The selection is applied by grasppanda.ops.backends.configure, which is also the Python interface:

    from grasppanda.ops import backends

backends.configure({"fps": "reference"})      # for this process
with backends.override(knn="reference"):       # temporarily, for a comparison
    ...
print(backends.report())

    grasppanda train, test and infer apply runtime.ops when the run starts, and the backend each operator settled on is written to env.json in the run directory.

    The environment variable GRASPPANDA_OPS overrides the configuration for one process, either with one backend for all operators or with a list:

    GRASPPANDA_OPS=reference grasppanda test ...
GRASPPANDA_OPS=fps=reference,knn=compiled python my_script.py

    grasppanda env --json and the env.json of every run record what each operator uses on the CPU and on the current CUDA device, and why if that is not what auto would prefer:

    "ops": {
  "fps": {"requested": "auto", "cpu": "compiled", "cuda": "compiled"},
  "knn": {"requested": "auto", "cpu": "compiled", "cuda": "reference",
          "note": {"cuda": "the compiled library has no kernels for 'cuda' tensors: ..."}},
  "library": {"path": ".../grasppanda_ops_3a33d4588d6dade9.so", "cuda": false,
              "detail": "CPU kernels only (no CUDA 11.x toolkit ...)"}
}

    Building the kernels¶

    The kernels are compiled the first time an operator needs them, with PyTorch's own extension tooling (torch.utils.cpp_extension), and cached. The build takes a few seconds: the kernels use no PyTorch headers and are called through ctypes.

    Needed For Without it
    A C++ compiler ($CXX or c++) and ninja (pip install ninja) CPU kernels One log line per process; every operator runs on the reference. Selecting reference (GRASPPANDA_OPS=reference) silences it.
    A CUDA toolkit of the major version PyTorch was built with CUDA kernels CPU kernels only; operators on CUDA tensors run on the reference. 
    python -m grasppanda._ops.build            # build if needed, then report
python -m grasppanda._ops.build --force    # rebuild, also after a recorded failure
python -m grasppanda._ops.build --cpu-only
    • Cache. $GRASPPANDA_OPS_CACHE, by default <cache root>/ops ($GRASPPANDA_CACHE or ~/.cache/grasppanda). One directory per PyTorch version, variant (CPU or CUDA), platform and source revision, so several environments share a cache without clashing and an upgrade rebuilds. Nothing compiled is ever part of the package.
    • Toolkit. $CUDA_HOME, nvcc on the path and /usr/local/cuda* are examined; a toolkit of exactly PyTorch's CUDA version wins, then any of the same major version. The kernels are compiled to PTX for the oldest GPU architecture PyTorch supports and specialised by the driver on first use, so one build serves every GPU of a machine and a build made on a login node serves its compute nodes. TORCH_CUDA_ARCH_LIST overrides the architecture list as for any PyTorch extension.
    • Failures. A failed build is recorded with its log next to where the library would be, reported in one log line, and not retried until the compiler changes or --force is given. A failed CUDA build still yields the CPU kernels.
    • Never on first use. GRASPPANDA_OPS_BUILD=0 uses a library only if it is already built.
    • Forked workers run the CPU kernels on one thread (GNU OpenMP does not survive a fork); the parent uses torch.get_num_threads().

    Changing an operator or adding a kernel¶

    • The reference comes first. Change behaviour there, with an oracle test written out in tests/unit/test_ops.py.
    • A kernel is accepted when it returns identical integers and bit-identical distances on tests/unit/test_ops_equivalence.py and tests/integration/test_ops_cuda.py, and when the GSNet parity and backbone oracle tests pass with it as default. Add the cases your change makes interesting to the randomized comparisons, and a self-check to grasppanda/ops/backends.py.
    • Where the reference goes through arithmetic that cannot be mirrored (a BLAS, a library function that is not correctly rounded), let PyTorch compute that part, or decide only what is certain and hand the rest back, as the cylinder query does.
