    Components¶

    Everything a config can name with type:, slot by slot. The page is generated from the registries, from what each class declares about itself and from the shipped configs, so it shows what is in the code, not what was planned. The same tables in a terminal:

    grasppanda components                    # every slot
grasppanda components --slot backbones   # one slot, with the meaning of its columns
grasppanda components PTv3               # one component: options, configs, what it fits
grasppanda components --json             # for scripts

    Which components can replace which, and what a swap changes besides the line in the config, is the subject of Swapping components. Turning a combination into a checked config and trying it on real frames is Try a combination; what that gave for every component under every method is Measured combinations.

    How to read the tables¶

    • Contract columns (between the name and the status) are the class attributes the config checker compares before anything is built. Each slot explains its own.
    • Status is what has been proven. tested: unit tests on CPU cover the component's contract and behaviour; for the stages of a ported method, the method's page under Model zoo says how it was compared with the reference implementation. weights-verified: additionally, weights released by the authors load strictly and the outputs match the official implementation; the measured difference is on the scene encoder page. bridge: the component is an adapter around a library installed as an optional extra; the library's own code runs, and the tests here cover the adapter (contract, shapes, gradients), not the library. —: the class declares no status. No status is a claim about grasp-detection accuracy.
    • Source is the paper, method or library the component implements, and where the code comes from: written for GraspPanda from the paper and the behaviour of the reference code (the ported grasp methods; licences and commits of the references are in the method READMEs), a bridge to a library, or adapted from permissively licensed code (listed in THIRD_PARTY_NOTICES.md).
    • Needs lists optional dependencies (pip install -e ".[...]").
    • Shipped configs are the runnable configs under configs/ whose resolved tree names the component.
