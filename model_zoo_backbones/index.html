    Encoders checked against their authors' code¶

    Each scene encoder below was checked to one of three depths. Nothing here is a grasp-detection result: the claims are about architecture fidelity, not accuracy.

    • Weights verified (5): PointNet2, PTv3, PTv3Sonata, PTv3Utonia, LitePT. Released weights load strictly, and the outputs match the official implementation.
    • Compared on synthetic weights (3): PointNeXt, OACNNs, SpUNet. The outputs match the official code when both are given the same analytic or hashed weights; no released checkpoint was loaded.
    • Unit-tested only (4): PointNet2Dense, FeaturePropagation, FurthestPointSubsample, MinkUNet. Unit tests only: not compared with the authors' code.

    Every registered encoder, checked or not, is in Registered classes; how each fares under every method is on Does it run?.

    What the status means¶

    Status Meaning
    tested Unit tests on CPU: output shape and channels, binding to the right point set, gradients reaching every parameter, deterministic evaluation, batch independence, variable-size batches, rejection of misuse.
    tested + parity Additionally: the outputs match the official implementation when both sides are given the same analytic or hashed weights. No released checkpoint was loaded. The measured difference is stated.
    weights-verified Additionally: a checkpoint released by the authors loads with no missing and no unexpected key, and the outputs match the official implementation run on the same input. The measured difference is stated.

    "Matches" is always a number. All comparisons are in strict float32 on one fixed 20 000-point tabletop scene, on CPU and on an RTX A6000; the fixtures and the script that recorded them are in the repository (see Reproducing the evidence).

    "Analytic" weights: both sides fill every tensor of their state dict with the same closed-form function of the tensor's name and shape. It needs no file, exercises options no released checkpoint uses, and fails if the two state dicts differ in a single key or shape. The fixtures are sensitive to the details that matter: for example, fusing before the decoder's positional convolution moves the PTv3 output by 1e-2, another curve order by 4e-2, and dropping the radius normalisation moves the PointNeXt output by 3e-3, all orders of magnitude above the agreement in the table.

    "Hashed, batch norm calibrated" is the same idea for deep batch-norm networks, which the analytic weights do not survive: a sine of the flat index makes every weight matrix nearly rank two, and batch norm with made-up running statistics normalises nothing. Through the 23 residual blocks of the published OA-CNNs the features then reach 3e2 and rounding alone separates the two implementations by 1.3 on the GPU; with calibrated statistics but sine weights, one and the same model still disagreed with itself between CPU and GPU by 3 % of its features. For these fixtures every value is a 32-bit integer hash of the tensor's name and flat index (exact on every platform, full-rank matrices), and each side then sets the batch-norm statistics with one training-mode pass of its own code over the input, so the comparison covers batch norm in training mode as well. Sensitivity, measured the same way: keeping the voxels the official OACNNs loses at an odd axis (crop_odd_extent: false) moves the published configuration by 1.6; anchoring its pooling grids at cell 0 instead of the lowest occupied cell moves the crafted-cloud fixture by 1.1 and the tabletop scene not at all, which is why that fixture exists; dropping the 1e-6 of the voting softmax fails the published configuration. For SpUNet, reading a 1×1 kernel the way its shape suggests moves the two fixtures by 15.7 and 0.49, and counting cells from one cell further by 9.1 and 0.31.

    Additional checks that need no oracle and run in the unit suite: PointNet2 and PointNet2Dense equal the paper's definition written out point by point in NumPy (float64, 1e-10) for five configurations; the Hilbert code equals Skilling's algorithm and visits every cell of a cube once through face neighbours.

    OACNNs has its own: the first block of a small network equals the adaptive aggregation written out cube by cube in plain loops, on a batch of two clouds one of which does not start at cell 0 of its level; an isolated voxel in the lost cell of an odd axis leaves the features of the rest of its cloud untouched; clouds with different bounding boxes do not interact. Together they pin what a single-cloud oracle cannot see: the per-cloud bounding box and the per-cloud softmax shift. For SpUNet, a converted 1×1 kernel is compared with the 1×1 convolution of spconv itself.

    One caveat for anyone repeating this on a GPU: PyTorch lets cuDNN compute convolutions in TF32 by default. On the A6000 that alone moves the PointNet2 features by 4.6e-3, in the official implementation too. The comparisons switch it off; normal use does not.

    LitePT: two reference outputs

    The official LitePT attention has no float32 path. It casts queries, keys and values to float16 and calls flash-attention, so "the official output" exists in two forms, and the fixtures hold both:

    • Attention in float32: the official forward pass with that cast switched off (Tensor.half returns its tensor while recording, and a plain softmax attention stands in for flash-attention, which accepts float16 only). This is the computation the port performs, and the one the table above compares with.
    • As released: the official forward pass untouched, with flash-attention 2.6.3 and the authors' CUDA PointROPE extension.

    The port differs from the model as released by what float16 attention costs the official model itself:

    Weights Official model, float16 against float32 attention (all points) LitePT against the official model as released (stored rows, CPU / CUDA)
    LitePT-S, ScanNet 7.5e-4 5.1e-4 / 5.1e-4
    LitePT-S*, ScanNet instances 2.0e-3 9.2e-4 / 9.2e-4
    LitePT-B, Structured3D 7.4e-4 5.4e-4 / 5.3e-4
    LitePT-L, Structured3D 6.4e-4 4.7e-4 / 4.7e-4

    With analytic weights the logits, and with them the effect of the cast, are arbitrary (6.1e-5 for the first analytic model, 6.3e-2 for the second), so only the float32 form is compared there.

    The released-weight fixtures use 1.25 mm voxels. The published models attend only after three poolings; at that grid the two attending stages hold 4 265 and 1 215 voxels of the scene, several patches of 1024 with an incomplete last one, where 5 mm would leave them 308 and 80 voxels, one patch each. The fixtures are sensitive to what matters: a PointROPE base of 90 instead of 100 in one stage moves the LitePT-S output by 5.5e-2, a patch size of 512 in one stage by 0.23, two curves swapped by 0.42.

    All six references were also recorded without flash-attention and without the compiled extension: the official PyTorch fallback of PointROPE, the plain attention on float16 and on float32 inputs, PyTorch 2.7.1. The port agrees with those to 2.7e-5 or better too. Where both attention backends ran on the same float16 inputs they differ by 4.8e-4 to 9.2e-4 with the released weights: the order of the float16 effect itself, and far below what a difference in meaning causes (5e-2 and more, as above).

    The PointNet++ family is slow for its size because it runs on the pure-PyTorch reference operators: furthest point sampling is a Python loop of one step per sample, so most of the time is interpreter overhead, which is also why batch 4 costs about the same as batch 1. A compiled sampling backend, held to the reference by the operator tests, is where that time would go.

    The OACNNs and SpUNet rows come from a later session with the same protocol (load average about 30; the batch of four is the scene, two mirrored copies and a shifted one). OACNNs spends its time in about two thousand small operations, the voting and pooling of four grids in each of 23 blocks, not in convolutions. It has no row at 0.02 m: the scene is 15 voxels deep there, and with the official bounding-box rule the network needs 16 along every axis (crop_odd_extent, below).

    Which file is "Concerto". The model card of Pointcept/Concerto says: "The default models(concerto_large/base/small/tiny) are the pre-release version of our next work, Utonia, which can deal with input without color and normal. If colors and normals are not available, please set them to zeros. [...] The original Concerto model is concerto_base_origin.pth." The four concerto_*.pth rows above are therefore the pre-release models, not the networks evaluated in the Concerto paper; the paper's are concerto_base_origin.pth and concerto_large_origin.pth. The activation fixtures of this page were recorded with the default files.

    All of them:

    • are encoder-only (enc_mode: true): the state dict has embedding.* and enc.* and no decoder. Dense features are the encoder stages concatenated through the pooling maps (concat_stages), the authors' linear-probing protocol. Setting enc_mode: false adds a decoder with random weights;
    • expect 9 input channels: coordinates, colour, normal. The authors advise zeros for a modality that is missing. The coordinate channels go through their data pipeline first (centring, and for Utonia a scale factor); reproducing that is the caller's job;
    • contain a mask_token that only pre-training uses; keep mask_token: true to load strictly;
    • store enable_flash: true. That selects an attention backend, not an architecture; flash-attention is not used here and is not needed;
    • are non-commercial by the stricter of the two statements their authors make. Using them makes the resulting model non-commercial. GraspPanda does not ship or download them.

    Where the implementations deliberately differ from upstream¶

    Each difference exists for the scene-encoder contract (batch independence, deterministic evaluation, no compiled extra) and is exact for a single cloud.

    Every difference, and the upstream behaviours kept as options
    Topic Upstream Here Why
    PTv3 attention backend flash-attention in half precision; without it, the patch size shrinks to the smallest cloud of the batch scaled_dot_product_attention in the input precision with the fixed-patch layout of the flash path No extra dependency; a cloud's result does not depend on its batch neighbours
    PTv3 serialisation depth one depth for the batch, from its largest cloud; the Hilbert curve depends on it one depth per cloud Batch independence
    PTv3 order shuffling every forward pass, in evaluation mode too training mode only Deterministic evaluation
    PTv3 voxel representative a random point of each voxel (training transform) the first point of each voxel Deterministic; features go back to exactly the points that produced the voxel
    PTv3 multi-dataset norms (pdnorm_*, PPT) one set of normalisation layers per training dataset, chosen per sample by a condition one set, chosen when the weights are loaded (pretrained_condition); the model is a plain PTv3 The Backbone contract carries no per-sample dataset condition. The released ppt checkpoints load with the statistics of the chosen dataset; the other sets are dropped
    PTv3 cls_mode (encoder without decoder) returns the coarsest level enc_mode: true returns the deepest concat_stages encoder stages concatenated on every input voxel A scene encoder returns one feature per point; encoder-only checkpoints load strictly
    LitePT attention backend flash-attention on float16 queries, keys and values; there is no other path scaled_dot_product_attention in the input precision, on the same patches No extra dependency. Measured: with the released weights the official output itself moves by 6e-4 to 2e-3 between the two precisions
    LitePT PointROPE a CUDA extension, or a PyTorch fallback that looks the rotations up in a table computed in PyTorch from the grid coordinates No compiled code; equal to both (the evidence was recorded with each)
    LitePT serialisation depth one depth for the batch, from its largest cloud one depth per cloud Batch independence
    LitePT order shuffling at every pooling, on every forward pass, in evaluation mode too; the model's shuffle_orders only reaches the input level training mode only, at every level, switched by shuffle_orders Deterministic evaluation
    LitePT patch size of a decoder stage that attends ignored: the level keeps the layout its encoder stage computed has to equal the encoder's; anything else is an error An argument that silently does nothing is a trap
    LitePT voxel representative a random point of each voxel (training transform) the first point of each voxel As for PTv3
    LitePT enc_mode (encoder without decoder) supported not implemented No released checkpoint uses it, and the model then returns its coarsest level instead of dense features
    PointNet++ sampling below the first level searches again takes the first rows of the previous sample Identical result (furthest point samples are nested), about half the sampling time
    OA-CNNs sparse grid the bounding box of the batch, so which voxels a cloud loses at an odd axis (crop_odd_extent) depends on its batch neighbours the bounding box of each cloud Batch independence
    OA-CNNs voting weights exp(logit - m) / (sum + 1e-6) with m the largest logit of the batch; because of the constant, m changes the result m is the largest logit of the cloud Batch independence
    OA-CNNs pooling grids anchored at the lowest occupied cell of the batch at each level anchored at the lowest occupied cell of the cloud Batch independence
    OA-CNNs voxel representative a random point of each voxel (training transform) the first point of each voxel As for PTv3
    OA-CNNs arguments without effect (groups, enc_num_ref, dec_depth, down_ratio) accepted; none enters the computation, the decoder has no blocks not parameters A config key that changes nothing is a trap
    SpUNet 1×1 convolutions (the final layer, the projected shortcuts) spconv convolutions of kernel size 1, stored as (out, 1, 1, 1, in) and applied as that memory viewed as (in, out) facade Linear layers with an (out, in) weight The facade defines a 1×1 convolution as a linear layer; convert_pointcept_state re-lays an official state dict, changing no value
    SpUNet enc_mode (no decoder, one pooled vector per cloud) supported not implemented Not a scene encoder
    SpUNet voxel representative a random point of each voxel (training transform) the first point of each voxel As for PTv3

    Two upstream behaviours are kept as named constructor arguments because checkpoints depend on them: PointNet2.fps_skip_near_origin (the PyTorch sampling kernel never selects a point within 3.2 cm of the frame origin) and PTv3.fuse_before_decoder_cpe (in PT-v3m1 the first positional convolution of each decoder stage reads the skip features only). PTv3 follows the serialisation-depth rule of the original release, which its weights were trained with; Pointcept ≥ 1.6 adds one to the largest coordinate first, which differs only when that coordinate plus one is a power of two.

    OACNNs.crop_odd_extent keeps a third: the way the official model treats the border of its grid. It declares the sparse grid as the exact bounding box of the voxels, and a stride-2 convolution without padding cannot place the last cell of an axis with an odd number of cells. At every level the voxels in that cell are left out of the down-sampling and get zeros back from the up-sampling, and a cloud thinner than 16 voxels along any axis runs out of cells (the official code then stops inside spconv with "out spatial shape reach zero"; here the error names the cloud and says what to change). crop_odd_extent: false keeps every voxel and has no such limit; the two agree whenever every extent is a multiple of 16. A tabletop cloud is easily thinner than 16 voxels at the published 0.02 m grid (the fixture scene is 15 deep), so a grasp detector needs a finer grid or crop_odd_extent: false. The batch dependence that the per-cloud evaluation removes is not small: batching the fixture scene with its own left half moves the official features of the two clouds by up to 1.1 on features of magnitude 10.6 (published configuration), where a batch here reproduces the clouds run alone to 2e-5.

    At a 5 mm grid, what has to be re-tuned in OACNNs is point_grid_size: the pooling grids are counted in cells, so the published 8 to 16 cells of the first stage shrink from 0.32–0.64 m to 0.08–0.16 m. SpUNet has nothing counted in metres or cells besides the grid itself; its receptive field shrinks with the grid, as that of SparseUNet14 does. The official SpUNet pads its sparse grid, loses no voxel and does not depend on the batch (measured as for OACNNs: 3.4e-5 on features of magnitude 13.9, which is rounding).

    Reproducing the evidence¶

    The unit suite needs no files; the oracle comparisons need the checkpoints named below.

    Commands and environments 
    # unit suite: contracts, written-out oracles, published sizes (CPU, no files needed)
pytest tests/unit -k "backbone or ops"

# oracle comparisons; the analytic ones run anywhere, the others need the checkpoints
GRASPPANDA_WEIGHTS=/path/to/weights pytest tests/integration/test_backbone_oracle.py -rs

    $GRASPPANDA_WEIGHTS holds graspnet_baseline/checkpoint-rs.tar, components/concerto_{tiny,small,base,large}.pth, components/utonia.pth and components/scannet-semseg-pt-v3m1-0-base.pth. A test is skipped when its file is absent and fails when the file's SHA-256 is not the recorded one.

    The fixtures themselves are re-recorded with tools/make_backbone_fixtures.py, which runs the official code and is documented in its docstring. It never imports grasppanda; the packages an oracle needs (torch_scatter, timm, addict, the compiled extensions of graspnet-baseline and openpoints) belong in a separate environment.

    LitePT has its own test file and four more checkpoints, all MIT:

    # components/{scannet-semseg-litept-small-v1m1,scannet-insseg-litept-small-v1m2}.pth,
# components/structured3d-semseg-litept-{base,large}-v1m1.pth
GRASPPANDA_WEIGHTS=/path/to/weights pytest tests/integration/test_backbone_litept_oracle.py -rs

    Its fixtures were recorded in an environment built for the purpose: PyTorch 2.4.1 + cu118 (the newest release flash-attention publishes a cu118 wheel for), flash-attention 2.6.3, spconv 2.3.8, torch_scatter, timm, addict, colorhash, NumPy 1.26, and the official PointROPE extension compiled out of tree for the GPU at hand, as its README instructs. Without flash-attention and the extension make_backbone_fixtures.py litept still runs, on the official PyTorch PointROPE and a plain softmax attention, and writes into the fixture which backend it used.

    The sparse CNNs of Pointcept have their own test file, which needs no checkpoint:

    pytest tests/integration/test_backbone_sparse_cnn_oracle.py -rs

    Their fixtures were recorded from Pointcept at commit 1342eda (MIT), unpacked from the GitHub archive, with spconv 2.3.8, timm, torch_geometric 2.6.1 and torch_cluster 1.6.3 (torch_geometric 2.8 moved the grid clustering OA-CNNs uses into pyg-lib). The recorder imports the official model file without pointcept/models/__init__.py, which would pull in every model of the zoo and its compiled extensions; no upstream code is stubbed or modified.
